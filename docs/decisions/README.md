# Decision register

Every significant or hard-to-reverse choice in TITAN, for every repository,
is a row in this one table: the question, the options considered, the
decision and why. The owner makes the decision; AI may prepare the options. A
row is never filled in with a decision the owner did not make.

- **The documentation describes how things are now**; this register says why.
  Docs link to the row that explains a choice instead of repeating it.
- **A changed decision is an edited row.** The old decision and its reasons
  stay in git history; the pull request that changes the row says what
  changed and why.
- **When the reasons do not fit in a row,** they get a section under the
  table, linked from the row, like [plugin trust](#plugin-trust-9). A separate
  file is the exception, for analyses too long for this page.
- Statuses: **Decided**, **Open** (options known, decision pending),
  **Later** (decided together with a later stage).

## Plugin trust (#9)

A plugin is code that has not passed our tests and review, yet runs next to
health and money data.

| Option | How it works | Isolation | Cost |
|---|---|---|---|
| A. Python package in the node process | The owner installs a package; the node loads its tools like built-in ones | None: the plugin sees the whole database, secrets and network | Simplest; trust rests entirely on whoever installs it |
| **B. Container with a manifest (chosen)** | A plugin is an image plus a manifest (tools, their classes, domains it needs, network destinations). The controller runs it; the node talks to it over MCP; it reaches data only through the API with a token limited to the granted domains | Strong: no database or secrets, network by allow-list, resource limits | Needs a manifest, scoped tokens and the controller to run it |
| C. WebAssembly sandbox | The plugin is compiled to WASM and runs inside the node through an engine such as Extism | Strong, but only what the engine allows | Few libraries; plugins are much harder to write |

Whatever the option:

- The owner approves the install after seeing the manifest: which tools, which
  data, which network destinations.
- The version is pinned by digest; an update with a changed manifest needs a
  new approval.
- The plugin declares the action class, but the node may only raise it: any
  plugin tool with network access counts as at least `external`.
- Every plugin call is written to the audit log, like built-in calls.

## Plugins on other machines (#21, #22)

A plugin may run on another machine, for example a work laptop. A small
TITAN agent on that machine hosts the plugin and connects out to the node
over HTTPS; it is paired like a device, with its own revocable token, and the
owner approves its manifest like any plugin's. Its tools are available to the
agent only while the connection is up; when it is offline, a call answers
"unavailable" at once and the agent says so.

### Confidential data

Before anything leaves the plugin's machine, confidential values are replaced
with placeholders, and the same value always gets the same placeholder within
a thread:

```
"Meeting with Ivanov on project Alfa, budget 120 000 EUR, ivanov@corp.example"
→ "Meeting with ⟦PERSON_1⟧ on project ⟦PROJECT_1⟧, budget ⟦AMOUNT_1⟧, ⟦EMAIL_1⟧"
```

When Claude calls one of the plugin's tools with placeholders ("write to
⟦PERSON_1⟧"), the plugin puts the real values back on its own machine and runs
the call there.

**What gets processed.** The manifest describes the output of every tool, and
marks fields as confidential:

| Mark | Meaning | Example |
|---|---|---|
| none | Sent as is | A meeting's start time and duration |
| `replace` | The whole value becomes one placeholder | An attendee's email address |
| `scan` | Free text is searched, and only what the detector finds is replaced | The body of an email |

By default only marked fields are processed. A plugin can be set to scan every
text field instead.

**The placeholder table** is kept, per plugin, either only on the plugin's
machine (real values never leave it; clients elsewhere show placeholders) or
on the node (real values can be shown on every client). What TITAN stores from
a plugin, in notes, memory or chat history, is stored with placeholders when
the table stays on the plugin's machine.

**Encrypted backup of the table (optional, off by default).** When the table
is kept only on the plugin's machine, the agent there can back it up to the
node, encrypted on the plugin's machine before it is sent. The node stores
only the encrypted copy and cannot read it; restoring it on a new machine
needs the key, which opens with either of two secrets: a passphrase the owner
remembers or a recovery key stored offline. The owner turns this on per
plugin.

**The detector** combines exact rules (email addresses, phone numbers, IBANs,
keys and tokens, amounts) with a local model for names and organisations, and
optionally a small local LLM for meaning-dependent terms such as project
names. Any detector can miss something: this lowers the risk, it does not
remove it.

The detector, the agent's repository and language, and the stage are decided
in rows #80 and #81.
